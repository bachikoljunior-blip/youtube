## 2. 何を作るか

- **1日1本**（オーナー 08/31 の規則。09/04「目標以外全部外して良い」で床ではなくなったが、
  §1 の「量は毒」と一致するので既定はこのまま）。**作り置きなし。当日に予約。**
- **縦 1080×1920・60〜95秒のショート**。上限は `studio/cli.MAX_SECONDS`（95秒。09/05 20:xx に実物と文書がずれていたので、数はここに写さない）。
  60秒を越えてよい理由: 分かる説明に要る長さを削らない（オーナーの指示が「分かるように」）。
  短いほど良い実測は無い（27〜32秒の本も 150秒の本も、いまは同じ 60〜190回）。
  **秒数は同じ本文でも焼くたびに揺れる**（09/06 22:1x 実測: 466字 94.5秒 → 7字 足して 473字 で 92.0秒 ＝ 4.93〜5.16字/秒・±3%）。上限に 2〜3秒 以内で寄せた本は、次の回が work/ を作り直したときに越えることがある —— そのときは本文を疑わず数字を削る。台帳 `built` の `scenes` でコマ単位に比べる。
- **公開 10:00 JST**（§1 の時刻の帯。09:00〜13:00 のどこでも差は無い。10:00 は
  「当日に予約する」に対して、深夜〜朝の回に作業時間が残る時刻）。
- **題材**: 年金・税・社会保険で、**その人の生活に直に効く1つの数字**。実測で伸びた題は
  年金（繰上げ・繰下げ・加給・遺族）・医療費控除・ふるさと納税・退職金。
  1本 = 1つの結論。「知らないと損」の形ではなく、**「こう決まっている。あなたの場合は
  ここを見れば分かる」の形**。
- **声**: Google TTS `ja-JP-Chirp3-HD-Charon`（男声）。rate は台本の `rate` が正本（09/06 02:1x 実測: 文書 1.15・台本 1.2 でずれていた。数はここに写さない）。Neural2-D より自然。
- **絵**: 1コマ 1枚の静止画。大きい字（結論・数字）＋ 字幕（声と同じ文）。背景は
  GPT Image 2.0 の絵（`data/image_orders/` に注文 → 外の ChatGPT 毎時セッションが焼いて
  `assets/images/` に置く。約束は `docs/IMAGE_ORDERS.md`）。届いていなければ単色。

## 3. どう書くか（**ここがオーナーの指摘の当のもの**）

台本は **Fable（サブ本人）がセッション内で直接 書く**。`claude -p` で別の模型に書かせない
（高レバレッジの仕事は Fable、と 09/03 に決まっている。`claude -p` の中は effort も文脈も
制御しにくい）。形は `data/studio/scripts/<id>.json`（`studio/script.py`）。

書き方の決まり（**「ノーコンテキストで質問されたときの説明」と同じにする**）:

1. **1文目で、誰に向けた何の話かを言う**（「65歳を過ぎて働きながら年金をもらう人へ」）。
   数字から始めない。前置き・自己紹介は無し。
2. **知らない人に話す。** 制度名を出したら、その場で1文で言い換える（「厚生年金の分だけ。
   国民年金の分は数えない」）。言い換えられない語は使わない。
3. **数字は1コマに1つか2つ。** 前提（年収いくら・何歳）は数字より先に言う。
   「A と B を足して C。境目 D より上か下か」の順で、計算を声で辿る。
4. **例は1人。** その人の数字で最初から最後まで通す。途中で前提を変えない。
5. **最後に「自分の場合はどこを見れば分かるか」を1文**。そのあと1文で問いかけ（コメント）。
6. **ふつうの話し言葉。** 「〜です・〜ます」。体言止め・倒置・「〜という形」を使わない。
   1文 40字以内、1コマ 70字以内（`MAX_SAY`）。
7. **画面の大きい字は結論か数字**（16字以内・行は `\n` で書き手が切る）。字幕は声と同じ文。
8. **名乗らない。** 経歴・資格・「私は」を書かない（`script.HUMAN_CLAIM` が止める）。
   「〜すべき」ではなく「この前提ならこうなる」。
9. **声の中の漢字の並びは、全部 `yomi` で読みを固定する**（09/06 14:2x に「割れる語だけ」から変えた。
   オーナー 09/06 13:0x「漢字の読み変なのいっぱいだよ。今後一個も出ないように考えて」）。
   `lint` が、`yomi` にも助数詞（65歳・15万円・60か月）にも送り仮名つきの語幹（増える・待つ・多く）にも
   当たらない漢字の並びを全部 挙げる（`script.uncovered_kanji`）。**通るまで出せない。**
   **なぜ「割れる語だけ」では駄目だったか**: hear は whisper が書いた漢字を pykakasi で仮名に戻すので、
   TTS が「月15万円」を「げつ」と読んでも whisper が「月15万円」と書けば両側が同じ仮名になり **見えない**
   （`hear.py` の冒頭に書いてあった盲点。実測: hear 11/11 で出した本を、オーナーが聞いて「読み変なのいっぱい」）。
   守りは TTS の側（`customPronunciations`）にしか置けない。1本ぶんは 18〜20語（09/07 の本で 19語・TTS は全部 受けた）。
   送り仮名つきの語は `yomi` に入れても **TTS に送られない**（`tts.py` が漢字だけの語に絞る。旧 yomi の「長生き」がそれ）ので
   本文を言い換える（長生き → 長く生きれば・手取り → 税金を引いたあと・先にずらす → おくらせる・900万円分 → 900万円がもらえません）。
   助詞つきの1字（月に・先に・得か・額は・後で）は語幹ではないので `VERB_STEMS` に入れない —— `yomi` か言い換え
   （「月15万円」→「毎月15万円」。「月」だけを `yomi` に入れると「か月」まで「かつき」になる恐れ）。
   実測で割れた語（09/05・Chirp3-HD Charon）: **裸の「年」＋数字**（「年66万円」→ とし）→
   「1年で」「12か月で」に書き換える。「2階建て」は whisper が「2回立て」に聞くので照合が通らない →
   「土台と上乗せ」に。hear が `!!` を出したら、まず whisper 側か TTS 側かを見る（whisper 側の癖は `hear.to_kana` で吸う:
   空白・×÷・ヶ月・後）。**覆る条件**: 全語固定の本を 7本 出して、オーナーの「読みが変」が 0 なら、この形で正しい。
   1つでも出たら、その語が `yomi` に在ったか（＝ customPronunciations が効かなかった）を先に見る。
   **09/06 15:xx（optimizer・Fable）に、その「効かなかった」を先に測った** —— `yomi` は語によって効かない。
   単語だけを Chirp3-HD Charon に言わせ、漢字を禁じた whisper（下の §4 (2)）で聞いた実測: 効いた ＝ 大家→たいか・
   何人→なにじん・年→ねん・月給→つききゅう・送料→おくりりょう・給料→たまりょう・合計→あわせけい。**効かなかった ＝
   額→ひたい・額面→ひたいめん・年金→としかね・市場→いちば・辛い→からい・十分→じゅっぷん**（API は 200 で受け、音は既定の読みのまま）。
   ＝ **「TTS は全部 受けた」は「全部 その読みで言った」ではない。** 全語 `yomi` は続けてよいが（害は無い・効く語では効く）、
   読みが正しいことの証拠は hear だけ。だから hear を、漢字に戻される前の**音の仮名**で照合する形に変えた（§4 (2)・§6）。
   **覆る条件**: 効かない語の規則が分かったら（例: 辞書に無い読みは捨てられる）、その規則を `script.py` の lint に入れる。
   **09/06 17:3x（hourly）**: 規則はまだ分からないが、実測で効かなかった語のうち既定の読みが割れるもの（裸の 額・額面・市場・辛い・十分）を `script.YOMI_IGNORED` に置き、`lint` が `[?]` で名指しする（止めない。語を変えるのは書き手）。効かない語が増えたらそこに足す。
11. **「点」と小数を、声にも画面にも書かない**（オーナー 09/05〜06「ナレーションが点って言ってるとこだよ」
   「点って漢字で動画に出てる」）。`lint` が `say`/`show`/`sub` の「点」と `0.7` の形を止める（`script.TEN`）。
   率は整数になる単位で言う: 1か月 0.7% → **10か月で 7%**・1.42倍 → **42% 増えて**・153.6年 → 言わない。
   分岐点・時点・弱点・起点 のような語も同じ（旧作り 9本・82コマ に在った。言い換え: 分岐点 → 境目・時点 → とき）。
   説明欄には書いてよい（読まれない）。**覆る条件**: オーナーが「点はもういい」と言ったとき。
10. **根拠は `notes` に**（制度の条文・年度・式・計算）。説明欄にも前提と式を書く。

## 4. 毎本の出口（順番が固定。オーナー 09/03 11:05）

    (0) その本に打つ改善を全部 先に終える（§3 の書き直し・絵・題）
    (1) 分かりやすさの輪:  read（Haiku・冷読）→ critique（Sonnet・批判）→ 直す → **最初から評価し直す**
        終わり: critique の items の1番目が nitpick（「1番可能性が高いものがほとんど言いがかり」）
    (2) 読みの輪:          build → hear（faster-whisper に**漢字を禁じて**全コマを音の仮名で書かせ → janome で読んだ予定の仮名と、ゆるく照合。09/06 15:xx に変えた・§6）
                           `!!` は「音が予定と違う」であって「誤読」ではない。実測 09/06 の本（読みは正しい）で 3/11 が `!!`（しがつ→しなつ・ねんきん→ねんりんきぃ 型）。
                           **差を読んで決めるのは Fable**: TTS の誤読なら yomi か言い換え → build → hear。whisper の聞き違い（1〜2音の揺れ・数字の前後）なら通す。
                           `--medium` は速さ 2.5倍 で `!!` は減らなかった（6/11）。既定は small。
                           **09/06 22:xx（optimizer）に測って捨てた手**: wav の末尾に無音 1秒 を足してから聞かせても、コマ7 の末尾欠落は再現せず（同じ音で raw も pad も 0差 ＝ 欠落は small の揺れで、音の終わり方ではない）。頭に無音 0.3秒 を足すと コマ10 が「[1]、[2]、[3]…」の連打に崩れた。**無音の足し引きは入れない。** 残るのは medium の聞き直し（下）。
                           **09/06 19:4x（optimizer）から: small で `!!` が出たコマだけ機械が medium で聞き直し、差が少ないほうを採る**（`hear.check(escalate=True)`・台帳 `escalated`）。
                           実測: 17:2x に hourly が手で medium で確かめた 3コマ（コマ2・3・9。全部 whisper 側）が、そのまま機械で消えて 11/11。TTS の誤読は medium でも同じ差が残るので隠れない。
                           それでも残った `!!` を読むのが Fable の仕事（上の行）。
        終わり: 一致 N/N。外れたコマは yomi を足すか語を変えて build → hear をやり直す
    (3) 目で見る:          work/<id>/sheet.png を Read（字の折れ・重なり・空白）
                           実測 09/05: 18字×4行 の字幕で「1\n0万円」「10万\n円」と数字が折れていた → `slides.wrap` が数字のかたまり（数＋万千＋円/か月）を1語として扱う
    (4) 予約:              当日の 10:00 JST へ（`schedule --at 10:00`）。当日以外は道具が拒む。
                           10:00 を過ぎていたら、いまから 20分 以上あとの 00分 に置く（出さない日を作らない）

(1) の模型: 冷読は Haiku、批判は Sonnet（「単純な記録・定型検査は軽い模型」）。**直すのは Fable**。
実測（09/05・最初の1本）: 1周 ≈ 3分（critique 2分・直し・lint）。real は 5 → 7 → 2 → 1 と減った。
批判は毎回 何か見つけるので、**枠の 60分 前になったら、その時点の本で予約し、輪は次の回が続ける**（差し替えで良くなる）。
critique の物差し（`studio/critic.py`）: real ＝ そこで話を見失う／nitpick ＝ 補足があれば親切。60〜90秒 で全部は説明しない。
**「ほとんど言いがかり」かを決めるのは Fable（サブ本人）で、critic の札はその材料**。実測（09/05・7周）: critic は毎周
何かを real と呼び、5周目で「計算を見せろ」→ 6周目で「計算が多くて追えない」→ 7周目で「計算を見せろ」と揺れた。
**前の周に直した所を、逆向きに直せと言ってきたら、それは言いがかりの域 ＝ 輪を閉じる。** 実測 2回目（09/05 21:1x・8→9周目）: 8周目「コマ3 の『足す』が何か不明 → 『給料に足す』と書け」→ 直した → 9周目「『給料に足すのも』で混乱する」。同じ所を逆向き ＝ 閉じた。**閉じるときも、その周の nitpick で安く拾えるもの（年号を声で言う・説明前の制度名を出さない）は拾ってから閉じる。** 冷読（Haiku）の
言い返しが takeaway と一致していることが、閉じる前提（7周とも一致していた）。
(2) は模型を使わない（CPU の whisper `small`。1コマ 5秒）。怪しいときだけ `--medium`。

## 5. 1日の回り方と、回ごとの手

親（毎時の心拍）がサブを1体 立てる。サブは `docs/METHOD.md`（これ）を読み、
`python -m studio.cli status` を撃ち、**いま何時か・きょうの枠に本が在るか**で手を決める:

| 状態（JST） | 手 |
|---|---|
| きょうの枠が空・台本が無い | 題材を決めて台本を書く（§3）→ 画像を注文 → build → (1)(2)(3) → **当日なら予約** |
| きょうの枠が空・台本は在る | (0)〜(3) を回して予約 |
| きょうの枠に予約ずみ・まだ公開前 | **その本を良くする**: 台本を直す → build → (1)(2)(3) → `schedule --replace <前のID>`（前の本は private に戻す。消さない）。良くする所が無ければ短く終わる —— **あすの台本はこの時間帯は `optimizer` の持ち場**（下の表。09/06 08:xx に この行が「あすの台本を書き始める」と言っていて、下の表と食い違っていた） |
| きょうの枠が公開ずみ | あすの台本を書く・磨く（予約は明日の回が当日にやる）。公開ずみの本の数字を `measure` で台帳へ |

### 同じ周に2体 走るときの持ち場（2026-09-05 21:3x に決めた。理由は下の実測）

親は1周に `hourly` と `optimizer` の2体を立てる（`scripts/next_round.py` の ROLES）。上の表は
**どちらも同じ表を読む**ので、きょうの枠が公開ずみの時間帯（10:00〜24:00 JST ＝ 1日の 14時間）は
**2体が同じ台本ファイルに同時に手を入れる**。実測 09/05 20:2x〜21:2x: `hourly`（`b2169181`・`d427f3d6`）と
`optimizer`（この回・押す前に merge で捨てた）が **同じ `2026-09-06-zaishoku-62man.json` の同じ3つの欠陥**
（定期便→年金額改定通知書・コマ10 のボーナス÷12・「今年4月」→「2026年4月」）を **30分 差で別々に直した**。
どちらの直しも本物だったが、Fable 2体ぶんの critique（Sonnet 1周 2分）と build/hear が二重に走り、片方は丸ごと捨てた。
08/31 の `src/descriptions.py`（`d2c4cae2`／`a89ab889`・6分差）と同じ形。

持ち場（**ファイルで分ける**。時間で分けない —— 押す前の作業は git の窓に出ない）:

| 役 | 持つもの | 触らないもの |
