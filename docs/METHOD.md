## 1. なぜこの形か（`data/` の実測から。撃った数だけ）

`data/uploaded.jsonl` × `data/views.jsonl`（873本・33,735点）を 2026-09-05 に数え直した:

| 事実 | 数 |
|---|---|
| 1,000回を越えた本 | **39本・全部ショート**（08/15〜08/24）。長尺の最高は 25回 |
| ショートの再生は、いつ付くか | 公開 **6時間で最終の 70〜90%**。48時間でほぼ止まる（＝ Shorts フィードの「お試し配信」1回ぶん） |
| 1日に何本 出したか vs 1本あたり | ≤13本/日の日: 中央値 **836〜1,400回**／25〜32本/日の日: 中央値 **2〜7回** |
| 08/25 以降 | ≤11本/日でも中央値 **7〜220回**。09/01〜 1本/日で **60〜191回** |
| 公開の時刻（JST） | 09:00〜13:00 の帯: 中央値 500〜1,200回／14:00 以降: **0〜4回** |
| 高評価 | 1,441回の本で **0**。25本 見て likes は全部 0〜1 |
| 登録者 | **25人**（80,483再生・253本） |

読み方:

1. **配る力は YouTube が持っている**（登録者25人で1本 1,000回）。1本 1,000回の「お試し」は
   毎回 来る。**その先へ伸びるかどうかが、こちらの作りで決まる** —— そして 08/15〜 の
   39本は 1本も先へ行っていない（likes 0・登録 +0〜1）。お試しの視聴者が最後まで見ず、
   何も押さなかった。オーナーの「何言ってるかわかんない」は、これと同じことを言っている。
2. 08/25 以降の落ち込みは、08/20〜22 に 1日 25〜32本 出した後に始まった。**量は毒**。
   1本/日 に戻しても戻っていない（09/01〜 60〜191回）＝ チャンネル単位で配信が絞られている。
   **戻す手は「見られる本」を続けて出すことしか無い**（他に手が無いので、これは推測）。
3. 長尺は、この作り方では 1〜25回。**捨てる**（外の帯では長尺が伸びている実測が
   `data/niche_ceiling.jsonl` に在るが、それは「別の作り方の長尺」。いまは 1本/日 の
   全部をショートの改善に使う。覆る条件は §7）。

## 2. 何を作るか

- **1日1本**（オーナー 08/31 の規則。09/04「目標以外全部外して良い」で床ではなくなったが、
  §1 の「量は毒」と一致するので既定はこのまま）。**作り置きなし。当日に予約。**
- **縦 1080×1920・60〜90秒のショート**。上限 90秒（`studio/cli.MAX_SECONDS`）。
  60秒を越えてよい理由: 分かる説明に要る長さを削らない（オーナーの指示が「分かるように」）。
  短いほど良い実測は無い（27〜32秒の本も 150秒の本も、いまは同じ 60〜190回）。
- **公開 10:00 JST**（§1 の時刻の帯。09:00〜13:00 のどこでも差は無い。10:00 は
  「当日に予約する」に対して、深夜〜朝の回に作業時間が残る時刻）。
- **題材**: 年金・税・社会保険で、**その人の生活に直に効く1つの数字**。実測で伸びた題は
  年金（繰上げ・繰下げ・加給・遺族）・医療費控除・ふるさと納税・退職金。
  1本 = 1つの結論。「知らないと損」の形ではなく、**「こう決まっている。あなたの場合は
  ここを見れば分かる」の形**。
- **声**: Google TTS `ja-JP-Chirp3-HD-Charon`（男声）・rate 1.15。Neural2-D より自然。
- **絵**: 1コマ 1枚の静止画。大きい字（結論・数字）＋ 字幕（声と同じ文）。背景は
  GPT Image 2.0 の絵（`data/image_orders/` に注文 → 外の ChatGPT 毎時セッションが焼いて
  `assets/images/` に置く。約束は `docs/IMAGE_ORDERS.md`）。届いていなければ単色。

## 3. どう書くか（**ここがオーナーの指摘の当のもの**）

台本は **Fable（サブ本人）がセッション内で直接 書く**。`claude -p` で別の模型に書かせない
（高レバレッジの仕事は Fable、と 09/03 に決まっている。`claude -p` の中は effort も文脈も
制御しにくい）。形は `data/studio/scripts/<id>.json`（`studio/script.py`）。

書き方の決まり（**「ノーコンテキストで質問されたときの説明」と同じにする**）:

1. **1文目で、誰に向けた何の話かを言う**（「65歳を過ぎて働きながら年金をもらう人へ」）。
   数字から始めない。前置き・自己紹介は無し。
2. **知らない人に話す。** 制度名を出したら、その場で1文で言い換える（「厚生年金の分だけ。
   国民年金の分は数えない」）。言い換えられない語は使わない。
3. **数字は1コマに1つか2つ。** 前提（年収いくら・何歳）は数字より先に言う。
   「A と B を足して C。境目 D より上か下か」の順で、計算を声で辿る。
4. **例は1人。** その人の数字で最初から最後まで通す。途中で前提を変えない。
5. **最後に「自分の場合はどこを見れば分かるか」を1文**。そのあと1文で問いかけ（コメント）。
6. **ふつうの話し言葉。** 「〜です・〜ます」。体言止め・倒置・「〜という形」を使わない。
   1文 40字以内、1コマ 70字以内（`MAX_SAY`）。
7. **画面の大きい字は結論か数字**（16字以内・行は `\n` で書き手が切る）。字幕は声と同じ文。
8. **名乗らない。** 経歴・資格・「私は」を書かない（`script.HUMAN_CLAIM` が止める）。
   「〜すべき」ではなく「この前提ならこうなる」。
9. **読みが割れる漢字は `yomi` に入れる**（額・境目・月額・給料 …）。送り仮名つきの語は
   `yomi` に入らない（TTS が拒む）ので、本文をひらがなに直す（繰下げ → くりさげ）。
10. **根拠は `notes` に**（制度の条文・年度・式・計算）。説明欄にも前提と式を書く。

## 4. 毎本の出口（順番が固定。オーナー 09/03 11:05）

    (0) その本に打つ改善を全部 先に終える（§3 の書き直し・絵・題）
    (1) 分かりやすさの輪:  read（Haiku・冷読）→ critique（Sonnet・批判）→ 直す → **最初から評価し直す**
        終わり: critique の items の1番目が nitpick（「1番可能性が高いものがほとんど言いがかり」）
    (2) 読みの輪:          build → hear（faster-whisper で全コマ聞き取り → 予定の読みと仮名で照合）
        終わり: 一致 N/N。外れたコマは yomi を足すか語を変えて build → hear をやり直す
    (3) 目で見る:          work/<id>/sheet.png を Read（字の折れ・重なり・空白）
    (4) 予約:              当日の 10:00 JST へ（`schedule --at 10:00`）。当日以外は道具が拒む。
                           10:00 を過ぎていたら、いまから 20分 以上あとの 00分 に置く（出さない日を作らない）

(1) の模型: 冷読は Haiku、批判は Sonnet（「単純な記録・定型検査は軽い模型」）。**直すのは Fable**。
実測（09/05・最初の1本）: 1周 ≈ 3分（critique 2分・直し・lint）。real は 5 → 7 → 2 → 1 と減った。
批判は毎回 何か見つけるので、**枠の 60分 前になったら、その時点の本で予約し、輪は次の回が続ける**（差し替えで良くなる）。
critique の物差し（`studio/critic.py`）: real ＝ そこで話を見失う／nitpick ＝ 補足があれば親切。60〜90秒 で全部は説明しない。
(2) は模型を使わない（CPU の whisper `small`。1コマ 5秒）。怪しいときだけ `--medium`。

## 5. 1日の回り方と、回ごとの手

親（毎時の心拍）がサブを1体 立てる。サブは `docs/METHOD.md`（これ）を読み、
`python -m studio.cli status` を撃ち、**いま何時か・きょうの枠に本が在るか**で手を決める:

| 状態（JST） | 手 |
|---|---|
| きょうの枠が空・台本が無い | 題材を決めて台本を書く（§3）→ 画像を注文 → build → (1)(2)(3) → **当日なら予約** |
| きょうの枠が空・台本は在る | (0)〜(3) を回して予約 |
| きょうの枠に予約ずみ・まだ公開前 | **その本を良くする**: 台本を直す → build → (1)(2)(3) → `schedule --replace <前のID>`（前の本は private に戻す。消さない）。良くする所が無ければ、あすの台本を書き始める |
| きょうの枠が公開ずみ | あすの台本を書く・磨く（予約は明日の回が当日にやる）。公開ずみの本の数字を `measure` で台帳へ |

**台本は `data/studio/scripts/` に commit する**（次の回が磨き続けるため）。
**「出した」とは、この台帳 `data/studio/ledger.jsonl` に event が1行 足されること**:
`built`・`heard`・`cold_read`・`critique`・`scheduled`・`measured`・`image_ordered`。
回の成果はそれで数える。旧 `run_marker.py` は使わない（ship の種別・腕・moves の帳簿は、
実測で ship 244件・`--moves 0` 238件 ＝ 帳簿が動くだけで本が良くならなかった）。

**模型**: サブは Fable（「Fable のみ」100% なら Opus。親の `next_round_owner.py` が印字するとおり）。
効き目のある仕事（題材・台本・直し）はサブ本人。Haiku/Sonnet は §4 の (1) だけ。

## 7. 覆る条件（次の回が数字で見ること）

- **形（ショート 60〜90秒）**: 新しい作りの本を 7本 出して、48時間の再生の中央値が
  旧作り（09/01〜09/05: 60〜191回）を越えなければ、書き方ではなく形か題材が原因。
  そのときは長尺（外の帯で伸びている形）を 1本/日 の枠で試す。
- **likes / 登録**: 7本で likes 合計 0・登録 +0 なら、「分かる」だけでは押されない。
  最後の1文（問いかけ）の形を変える。
- **時刻 10:00**: 同じ本で 10:00 以外に出した実測は無い。7本 出したら
  `data/studio/ledger.jsonl` の `measured` で時刻別に並べる。
- **90秒の上限**: 維持率が Studio でしか見えないので、機械で測れる代わりの数は
  `measured` の 6時間再生／48時間再生の比。60秒以内の本と越えた本で差が出たら締める。
- **1日1本**: §1 の「≤13本/日 なら中央値 1,000回」は 08/15〜24 の話で、いまの絞られた
  チャンネルで同じかは分からない。**新しい作りで 7本 続けて 500回 を越えたら**、
  2本/日 を 3日 試して 1本あたりが落ちないか見る。
- **Chirp3-HD Charon**: 声で差が出るかは未測。7本 出すまで固定（同時に2つ変えない）。
