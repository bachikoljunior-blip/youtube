# 何が動かせて、何が動かせないか

**このファイルは分類のためだけにあります。** 中身の説明は各ファイルにあるので、
ここでは「誰が決めたか」だけを書きます。

なぜ要るか。`CLAUDE.md` も `docs/GOAL.md` も、**オーナーの指示とこちらの判断が
同じ命令口調で混ざっていた。** 後から来た側には、どれが動かせないのか分かりません。
その結果、**見直すべきものを聖域にし、守るべきものを勝手に変える**危険があります。

分類は2つだけです。

- **A. オーナーが指示したこと** — 勝手に変えない。変えたいなら**提案して確認を取る**
- **B. こちらで決めたこと** — **いつでも見直してよい。** 根拠と、覆る条件を併記する

**新しい規則を足したら、必ずここに分類を書くこと。** 書かないと、また混ざります。

### A15 について（2026-08-08 に追加され、A8 が消えた）

**トークンの予算制限は無くなった。** 以前あった A8（土曜07:00 区切り・週15%）は
**恒久指示から外れている。** オーナーの原文はこう:

> クロードのサブスクの使用量をあなた自身が見られる状態であることと、
> bachikoljunior@gmail.com のチャットgptをあなたが使えること、
> 少なくともチャットgptがチャットgptの使用量も見れること、
> **どちらの使用量もチャットgptsparkの使用量も全てあなたが使っていいこと**、
> simple のリポジトリのメイン以外の全てのリポジトリの内容は全て変えていいこと

**「使いすぎないように絞る」は、もう理由にならない。**
使い切れば止まるのは事実だが、**残すこと自体に価値は無い。**
やるべき作業があるなら、予算を理由に見送らないこと。

使用量の読み方（**2026-08-14 に読む先を変えた**）:

    list_sessions limit=25 mine=true          ← MCP。返りをまるごと保存する
    python scripts/quota.py --ingest <file>

**恒久指示ブロックにある `show-usage.mjs` は、もう値を返さない。**
`-chatgpt-usage-monitorPrivate` の OAuth が 8/11 に切れ、向こうの GitHub Actions も
8/12 09:39 JST から止まっている。**A15 は「使用量を自分で見られる状態にしておくこと」で、
`show-usage.mjs` で見ろとは言っていない。** 読む先はこちらの判断で変えてよい（A14）。

代わりに読むのは **CCR の MCP の返りそのもの**（`external_metadata` の
`rate_limit_info` と `usage`）。`add_repo` も Actions も要らず、遅れもない。
**ただし%は返らない**ので、`quota.py` が状態の遷移を積んで目盛りを後から決める。
詳細は `scripts/quota.py` の docstring と `docs/trigger_main.md` §2。

**`scripts/usage.py` は使用量の測定ではない。** オーナーが「なんの当てにもならない」と
明言した。残量を根拠に何かを決めるときに、あの数字を使わないこと。

### A14 について

**「この表以外は全部あなたが決めてよい」という指示です。** つまり:

- **B のどれも、数字か理由があれば変えてよい。** オーナーに確認を取る必要はない
- **「昔オーナーがそう言ったから」は理由にならない。** 言われた瞬間の指示と、
  恒久的に守るべき指示は別物。**A の表に無いなら、それは恒久指示ではない**
- **A に無いものを A のように扱わないこと。** それが一番よくある壊れ方です

**B を変えたら、理由を `docs/JOURNAL.md` に書くこと。** 承認は要らないが、記録は要る。

### A4 について

**「忘れない」ではなく「忘れないように設計する」。** 記憶に頼るなという指示です。

`scripts/goal_reminder.sh` が毎ターン発火し、**この表の A を機械的に抜き出して**
文脈へ戻します。**手で写さないこと** — 写すと必ずずれます
（実際「週100クレジット」が5ファイルに散った）。**この表を直せば注入も直ります。**

対象は目標だけではなく**恒久指示すべて**です。以前は `GOAL.md` を丸ごと
注入していましたが、**肝心の A が揃っていませんでした**（目標本文はあっても
リポジトリを伏せる・週300ドル・あらゆる手段を実行してよい、が入っていない）。
手順や方法論（B）ばかりが毎回入り、守るべきもの（A）が入っていないのは本末転倒でした。

**A を増やしたら、注入は自動で追随します。** 何もしなくてよい。
ただし**表の書式（`| A番号 | 内容 | 日 | 場所 |`）を崩すと抜き出しが壊れる**ので、
書式を変えたら `scripts/goal_reminder.sh` の正規表現も直すこと。

### A13 について

**これは許可ではなく指示です。** 「やってよい」ではなく「**やれ**」と読むこと。

つまり**自主規制で止まるな**ということ。具体的には:

- **承認を待たない。** できることは黙って実行する（A1 も「私が読むとは限らない」と言っている）
- **手段を狭く見積もらない。** ニッチ・尺・形式・頻度・チャンネル・言語・
  収益の立て方まで、**全部が対象**。いまの構成は出発点であって答えではない
- **「たぶん許されない気がする」で候補から外さない。** 外すなら理由を数字か事実で言う
- **既存の実装を惜しまない。** より速い道が見つかったら捨てる

**手段として成立しないもの**（制約ではなく、**目標を壊すので効かない**）:

- 再生数や登録者の購入、複数アカウントでの水増し、なりすまし、虚偽の数字。
  **見つかればチャンネルごと失う。** 収益化されなければ RPM がいくつでも収入はゼロなので、
  これは倫理の話である前に**期待値がマイナス**
- 法に触れること。同上

**この2つ以外で手を止めていたら、それは A13 に反しています。**
迷ったら実行して、結果を JOURNAL に書くこと。

### 許可されていること（やってもよいが、やる義務はない）

- **チャンネル名を変えてよい**（08-04）。ただし API では変更できない
  （個人チャンネルは `brandingSettings.channel.title` の更新が黙って無視される）。
  Studio が要るのでオーナーの作業になる。**読まれない前提で設計するので、依存しない**

**A1 は「制約は一切ない」と明言しています。** つまり A の表にあるもの以外は全部 B です。
迷ったら B に倒してよい。**聖域を増やさないこと。**

## B. こちらで決めたこと（いつでも見直してよい）

**「なぜ」と「何があれば覆るか」を必ず併記すること。** 理由の書いていない規則は、
次に来た側が判断できず、惰性で残ります。

### B1. 制度を解説せず、自分で計算した結果を発表する

- **なぜ** — YouTube の収益化ポリシーが「他人の資料の読み上げ」「量産テンプレート」を
  対象外と明記しているため。収益化されなければ収入はゼロなので、到達可能性の条件
- **覆る条件** — ポリシーを守る別の形（自分の声、実画面の収録、別形式）のほうが
  速いと分かったとき。**ポリシーは事実だが、守り方は他にもある**
- 詳細は `CLAUDE.md`「この作りの根幹」

### B2. 1本に chart を最低3枚（**長尺だけ。** `verify.py` が落とす）

- 最終確認: 2026-08-10
- **見出しが事実と違っていたので直した。** `verify.py:565` が
  `None if portrait else script` を渡していて、**縦向き（ショート）では
  枚数の判定そのものが走らない。** 意図的な作りだが、
  ここには「1本に」と書いてあり、**ショートにも当たるように読めた**
- **なぜ** — 棒の長さが計算結果なので、回ごとに図の形が変わる。量産判定を避ける
- **ショートに当てない理由（2026-08-10 に数字が付いた）** — 平均視聴は22秒で、
  30秒の動画なら**見られるのは2〜3枚**。そこに chart を3枚入れると
  ほぼ全部が棒グラフになる。**枚数より、冒頭で何を見せるかのほうが効く**
- **覆る条件** — 別の方法で「同じ絵の繰り返し」を避けられると分かったとき。
  枚数そのものに根拠はない（**3 は勘で置いた数字**）

### B3. ショートの1枚目は `stat`、**1枚目22文字・全体140文字（約30秒）**、ID は `s-<計算モジュール名>-<連番>`

- 最終確認: 2026-08-10
- **「60秒以内」は古い。** 2026-08-09 に 50秒 → 30秒 へ、さらに
  **1枚目を22文字（約4.2秒）**に絞った。文書だけが60秒のまま残っていた
- **なぜ1枚目を短くするか（実測）** — 維持率の最大の落差が **4.7〜5.7秒**なのに、
  旧設計の1枚目は 7.9〜13.8秒。**落差の瞬間、画面がまだ一度も変わっていない**
- **なぜ `stat` か** — 最初の1画面で離脱が決まると考えたため。IDは calc を自動で
  引くための規約
- **覆る条件** — 冒頭を chart にしたほうが伸びると数字で出たとき。**未検証**。
  1枚目の長さのほうは 8/26 に判定する（`config/hypotheses.yaml`）

### B4. 改正が続く数字は「入力」に逃がす

- **なぜ** — `src/calc/jutaku.py` で借入限度額を使わず年末残高を入力にした。

### B5. 目視は**ショートの contact sheet が必須**。長尺は要点だけ見る

- 最終確認: 2026-08-10
- **なぜ** — 画像の Read は高く、長尺は再生数がほぼ0で当たり率が効くのはショートだから。
  **2026-08-10 に測って裏が取れた**: 長尺は 8/4 以降で **1再生・1分**、
  視聴ページに来た人は28日で**2人**
- **ただし「長尺は見なくてよい」ではない（2026-08-10 に足した）。**
  この規則は**費用の話**であって、見なくてよい理由ではない。
  実際この日、長尺・ショートとも**1枚目とサムネだけは毎回見て**いて、
  そこで2回止めている:

      `tenshoku-nenshu` … 初稿が既存ショートと同じ棒を出していた
      `s-fukugyo-2`     … 題が「助言」に読める形で、**サムネと食い違っていた**

- **機械が見ていないものがある。** 検査が落とすのは数字が計算に無いときだけで、
  **「言い方が angle と食い違う」「題とサムネが別のことを言っている」は誰も見ない。**
  目視の役割は折り返しの崩れだけではない
- **覆る条件** — 長尺が伸び始めたとき（そのときは contact sheet も長尺に広げる）

### B6. しきい値は掛け算してから置く／検査は壊れたものだけ／故障を注入して発火を確かめる

- 最終確認: 2026-08-10
- **なぜ** — 単色サムネのしきい値をバイト数で勘に置いて素通りさせた。
  登録率の反証条件を100再生に置いて、期待値0.3人で何も検出できなかった
- **2026-08-10 に1項足した: 検査を作った回・直した回は、その検査の偽陽性を測ること。**
  8/9 だけで**4回**、道具のほうが間違っていた:

      `_to_yen`      「35万9318円」から 9,318 を二重に拾い、正しい題を落とした
      `_to_yen`      「35.9万」で `9万` に食いつき 90,000 を返した（理由が嘘になる）
      `audit` の判定  `sort` 忘れの400を「API の制約」と誤って記録した
      `scan` の窓    移動窓のまま差分を出し、一律 −16 を「減少」に見せた

  **どれも静かに通り、もっともらしい説明まで付いていた。**
  「落ちるべきものが落ちるか」（故障注入）だけでなく、
  **「通るべきものが通るか」を既存の実物で必ず確かめること。**
- **覆る条件** — 覆らないはず。これは方法論であって内容の判断ではない

### B7. 律速は登録者（ただし根拠を 2026-08-10 に置き換えた）

- 最終確認: 2026-08-10
- **結論は変わらないが、根拠は全部書き直した。** 元は「登録率0.3%なら
  登録者側が約33万再生・総再生時間側が約6万再生」。**0.3% は実測で外れ、
  4,000時間の見積もりも間違っていた。**
- **実測して掛け算し直した（2026-08-10）**

      登録者          2 / 1,000                    → **500倍 足りない**
      ショート再生    約72,000 / 1,000万（90日）   → **139倍 足りない**
      長尺の視聴時間  **0.02時間 / 4,000時間**     → **20万倍 足りない**

  長尺の視聴時間は API で直接測った（`creatorContentType=videoOnDemand` が
  8/4 以降で **1再生・1分**。ショートは 4,368再生・621分）。
- **門は2つあり、どちらも登録者1,000人を要求する。** 違うのは2つ目の条件で、
  ショートの道は「90日で1,000万再生」、長尺の道は「4,000視聴時間」。
  **ショートの視聴時間は4,000時間には数えられない**（だから門が分かれている）
- **だから「律速は登録者」は、いま乗っているショートの道では正しい**
  （500倍 > 139倍）。**長尺の道は20万倍で、比較にならない**
- **これは M4 の位置づけを変える。** 長尺は「もう1つの流入源」ではなく、
  **長尺の道を0%から立ち上げる唯一の手**。いま 0.02/4,000 時間
- **覆る条件** — 登録率が実測で動いたとき、または長尺の視聴時間が
  1桁でも増えたとき（いまは 0.02時間なので、**1時間になっただけで50倍**）

### B8. 予約は数日先まで埋める。ショートは09:00 JST、長尺は19:00 JST

  ので、09:00 の根拠は弱い
- **覆る条件** — 時間帯べつの実績が出たとき。まだ出していない

### B9. 仮説に反証の期限と条件を切る（`config/hypotheses.yaml`）

- 最終確認: 2026-08-10
- **なぜ** — 期限を切らないと推測が永久に推測のまま残るため
- **2026-08-10 に3項足した。** 期限と条件を書くだけでは足りないと分かった:

      **判定に使う指標を名指しする** … `statistics.commentCount` は自分の
        コメントを数え、Analytics の `comments` は数えない。**取り違えると
        視聴者0でも半分通る**
      **母数を確かめる** … 8/19 の基準を「既存5本」で書いていたが、
        予約ぶんを調べたら同じ設計が11本あった。**n=5 の中央値は弱い**
      **窓を揃える** … 検索の基準を28日の37と比べようとしていた。
        判定は7日で見るので**名残が抜けるだけで「減った」に見える**

- **待つと決めたら、待つ先より予約の切れる日が後か確かめること**（8/10 に踏んだ）。
  「8/26 の判定を待つ」と書いたが、**予約は 8/21 で切れていた**
- **覆る条件** — 覆らないはず。これも方法論

### B10. ショートは1日1本に絞る

### B11. 常時稼働はしない。定期実行は1時間おきに1回、終わったら終わる

- 最終確認: 2026-08-09
- **2026-08-09、オーナーの指示で1時間おきになった**（それまで6時間おき）。
  **間隔はもうこちらの裁量ではない。** ここは B ではなく実質 A に近い
- **1回を小さくすること。** 168回/週なので、1回で全部やろうとしない。
  「今回は何もしない」も正しい
