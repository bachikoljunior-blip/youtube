# 自動実行（トリガー）の正本

**この運用は永久に続けるものです。** 止めない。人が思い出して直す前提にしない。

自動実行はこのリポジトリの外（Claude Code の Routine）にあるので、壊れたり消えたり
したときに**中身をここから復元できる**ようにしてある。トリガーの設定を変えたら、
このファイルも同時に直すこと。

---

## いまの設定（2026-08-10 に親子方式へ変えた）

**オーナー指示（2026-08-10）**:
「現行の定期実行で毎回新しいセッション立ててそこで実行するようにして。
そのセッションが終わったらアーカイブするようにして」
のあと
「**新しいセッションの立て方は eta改善ループでやってるやり方にして**」。

長いセッションで判断が雑になるのを避けるため（恒久指示 A12）。

| 項目 | 値 |
|---|---|
| trigger_id | `trig_01S5mtxkjiBp6hsttmDvdzgw` |
| cron | `9 * * * *` |
| 起動先 | 常駐セッション `session_01PXy8TiBxL1SM7AUc6XAMML`（`persist_session: true`） |
| 環境 | `env_01QMJaP2yRCzw4tY5VpJeM1m` |
| 親の役目 | **子を1つ立てる／終わった子を畳む。それだけ。周は回さない** |
| 子の役目 | **その回の仕事を全部やって、自分を archive する** |

### `create_new_session_on_fire` は使わない

一度そちらで作って、**同じ日に消した。**

**姉妹ループ2件が「撃っても一度も起動しなかった」と実測している**
（note 2026-08-08「観測2つ」／eta-loop 2026-08-09「実測で一度も発火しません」）。
**動いている自動実行はすべて `create_session` 方式。**
オーナーも「eta改善ループでやってるやり方にして」と名指しした。

さらに作った直後、**「このトリガが起こすセッションは MCP ツール無しで走る」**
という警告が出た。MCP が無ければ子は自分を archive できない ——
**依頼の後半がそもそも成立しない。**

### 子の立て方（`create_session`）

    source_url:      https://github.com/bachikoljunior-blip/youtube
    source_revision: claude/youtube-auto-post-revenue-ggedij
    extra_allowed_tools: ["Bash","Read","Write","Edit"]

**`source_url` を忘れるとリポジトリが無い状態で始まる**（note 側で1回やっている）。
**`source_revision` を忘れると main で始まり、成果がどこにも残らない。**

子に渡す本文は **`docs/trigger_main.md` を読ませる**趣旨にする。
**事実を書き写さないこと。写した瞬間に古くなる。**

### 二重に立てない

    python scripts/run_marker.py --window 40

子は最初に `--write` を打つ。**40分以内に印があれば親は立てない。**

### 畳み方

子が自分で `archive_session` を呼ぶ。**自分のIDは推測せず環境変数から:**

    echo "session_${CLAUDE_CODE_REMOTE_SESSION_ID#cse_}"

呼べなかった子のために、親が毎回掃除する:

    python scripts/run_marker.py --sweep              # 畳んでよいIDを出す
    python scripts/run_marker.py --swept <ID> ...     # 畳んだら記録

**`list_sessions` から名前で探さないこと**（似た名前の別セッションを畳む事故）。
`--sweep` が出すのは **`data/runs.jsonl` に子が自分で名乗ったIDだけ**、
かつ **90分より古いもの**。二度畳まないよう `data/archived_sessions.json` に記録する。

**ただし子が止まっている疑いがあるときは `list_sessions` で状態を見る。**
`REQUIRES_ACTION` は生きているのではなく**止まっている**。承認待ちの子は永久に待つ。

### 生存判定に git のコミット時刻を使わない

このブランチには姉妹ループも push する（8/10 に実例）。
**別のものを数えている指標を「生きている証拠」にしない。**

**親自身の印も生存の証拠にしない。** 親が `--write` を打つと、
次の回の親が「生きている」と読み、**親どうしで生きているふりが成立する。**
規律ではなく機械で外してある（`run_marker.py` の `WATCHDOG_SESSION`）。

## 間隔を変える判断

**予算では決めない**（A15「使用量は全部使ってよい」）。決めるのは**律速**。

- **1時間おきの根拠** — 2026-08-09 にオーナーが指示。**これはオーナーの指示なので、
  こちらの判断で戻さないこと**（間隔の裁量は B11 にあるが、名指しの指示が優先）
- **1回を小さくすること** — 168回/週なので、1回で全部やろうとしない。
  前の回の続きを1つ進めれば足りる。**同じ確認を毎回やり直さない**
- **頻度を下げてよい条件** — オーナーが下げてよいと言ったとき。
  「分析しても変えることが無い回が続く」は、1時間おきでは**下げる理由にならない**
  （何もしない回があってよい。それが1時間おきの前提）

## 落としても止まらない理由

**投稿が予約済みなら、起きなくても公開される。** だから間隔を落としても
チャンネルは動き続ける。逆に**予約が切れそうなときは、他を削ってでも生成に使う。**

`status.py` が「予約が入っていない日」を出すので、そこだけ見ればよい。

## 親が肩代わりするとき

親は普段、子を立てて掃除するだけです。**MCP が使えず子を立てられない回だけ**、
鎖を切らないために（恒久指示 A10）親が自分で1周します。

手順は `docs/trigger_main.md` の 1〜6 と同じ。**そちらを読むこと。**
ここに二重に書かない —— **二重に書いた瞬間に、片方が古くなります。**
（このファイルは 8/9 にまさにそれで壊れています。）

ただし **`--write` は打たないこと。** 親の印は子の生存の証拠になりません
（`scripts/run_marker.py` の `WATCHDOG_SESSION` の理由）。機械側でも弾いてあります。

## 本文の正本（トリガーが壊れたら、これを `prompt` に入れて復元する）

**ここは実際のトリガー本文と一致させること。** 片方だけ直すと、
壊れたときに古いものが復元される。

**2026-08-09、まさにそれをやった。** トリガーを3回更新したのに、
ここは1回目のままだった。**同じファイルに警告を書いた直後に破った。**
だから**更新の手順を決める**: トリガーを変えたら、**同じコミットで**ここも変える。

- **最終同期: 2026-08-10 11:03 JST**（この日付が古かったら、ずれている疑いを持つ）

**本文そのものは `docs/trigger_main.md`（本番）と `docs/trigger_parent.md`（親）**
に置いた。長いので、この表からは外してある。

**この2つは、API に投げたのと同じ文字列を同じ回に書いた。**
一度「API から書き出す道具でやる」と書きかけて消した。
**MCP はシェルから呼べないので、そんな道具は作れない。**
（存在しない道具を正本に書くのが、8/9 のずれと同じ壊れ方。）

**ずれていないかは `list_triggers` で確かめること。**
ファイルどうしを見比べても、トリガー側が変わっていたら分からない。
