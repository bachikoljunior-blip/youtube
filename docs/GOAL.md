# 目標（オーナーの言葉のまま。絶対に書き換えないこと）

> 目標は最短で月収20万を達成することです。最短とは、原理的に最大の理論値で、
> その理論値は空想のものであり、つねに発見、達成はできていないものと考えられます。
> その上で最短を目標としてください。それ以外の制約は一切ありません。あなたが
> できることは全て行っていいです。私側への指示をしてもいいですが、それを私が
> 必ず読むとは限りません

## 何かを決める前に、毎回この5つに答えること

**覚えているだけでは足りません。実際に適用したか、毎回確かめてください。**
過去に2回、覚えていたのに適用せず、オーナーに指摘されて直しています。

1. **いまのやり方が最短だと思っていないか。** 今日は何を変えるか。変えないなら、
   なぜ今日も同じでいいのかを言えるか。「前回そうしたから」「そう設定されているから」は
   理由になりません。ニッチも尺も形式も頻度もチャンネルも、変えてよい対象です。
2. **この判断の根拠は数字か、推測か。** 推測なら推測だと言ったか。
   自分の観測より、オーナーの経験や JOURNAL.md の記録のほうが強い証拠のことがあります。
   それを弱い根拠で上書きしていないか。
3. **オーナーの作業に依存していないか。** 指示は出してよいが、読まれるとは限りません。
   読まれない前提で成立する道を先に選ぶ。承認待ちで止まらない。
4. **投稿は途切れないか。** 途切れるのが最大の損失。ただし `src/verify.py` は迂回しない。
5. **ポリシーに触れていないか。** 量産テンプレート判定・他人の資料の読み上げは
   収益化そのものを失わせます。収益化されなければ RPM がいくつでも収入はゼロ。
   これは制約ではなく、到達可能性の条件です（`CLAUDE.md` の「この作りの根幹」）。

## 起きたら何をするか（上から順に、当てはまる最初の1つ）

定期実行は**毎時**撃ち込まれます。**「やることがない」という結論は禁止です。**
待っている時間は損失です。1回の起動につき、必ず1つ進めて JOURNAL.md に残してください。

0. **`python scripts/post_pending_comments.py` を実行する。** 数秒で終わり冪等です。
   予約公開した動画のコメントは公開まで書き込めない（private だと 403）ので、
   公開時刻をまたいで誰かが付けに来る必要があります。これを忘れると、
   **公開時刻にセッションが生きていなければ永久に付きません。**
1. **その日（JST）の長尺の投稿がまだなら、他の何より先に投稿する。** これは義務です。
2. **`python scripts/status.py` を実行する。** これ1つで、動画ごとの再生数・
   予約の状況・公開されないまま止まっているもの・流入経路・門までの距離が出る。
   API を叩いて頭の中で組み立てないこと。**組み立てると間違える**（実際に
   チャンネル総再生 5634 を成果と読み違えかけた。あれは前身のぶん）。
   読んだだけで終わらせず、**次に何を変えるかを決めて JOURNAL.md に書く**。
3. **ショートを1本出す。** 律速は登録者で、認知ゼロのチャンネルに露出が出る唯一の面。
   長尺は総再生時間を積む役、ショートは登録者を集める役。
   作り方は下の「ショートの作り方」。
4. `src/calc/` の在庫が薄ければ、次のテーマの計算を実装してテストまで通す（投稿はしない）。
   計算が先にあるほど、投稿の日は台本に集中できて速くなる。
5. `config/topics.yaml` に「計算で独自性を出せる切り口」が足りなければ、調べて足す。
   検索需要があって、かつ自分で数字を出せる題材を探すこと。
6. 維持率・CTR を上げる仕組みで、まだ試していないものを1つ実装する。
7. ここまで全部済んでいるなら、**その日の2本目を投稿する。** 本数は制約ではありません。

## ショートの作り方

    python -m src.pipeline --script build/short.json --topic s-<名前> --short --dry-run
    python scripts/upload_only.py s-<名前>

- テーマIDは **`s-` で始める**。topics.yaml に置かなくてよく、長尺のテーマ枠を消費しない
- 縦1080x1920。字幕は下から420上げてあるので、ショートのUIと重ならない
- **60秒以内**。ナレーション合計およそ300文字が目安（読み上げて約50秒）
- **1本＝1つの計算結果。** これで切り口も図も毎回変わり、量産判定を避けられる
- 長尺の8.5分の下限は適用されない（あれはミッドロール広告のための下限）
- 既存の `src/calc/` の数字をそのまま使えるので、長尺1本から何本も切り出せる
- **最後の1節で、次に何の数字が得られるかを言う。** 長尺の「登録依頼を書かない」規則を
  ここに流用しない。あれは長尺の維持率のための規則で、ショートは登録者を集めるために
  出しています。律速は登録者なので、ここを外すのは目的に反します。
  ただし「登録お願いします」ではなく、**続きに何があるかを具体的に言う**こと
  （効くかどうかは未検証。実績で確かめること）

1回の起動は短く独立に。前回の続きを記憶で追わず、JOURNAL.md と実績から読み直すこと。

## 投稿する前に必ず通すもの

    python scripts/inspect_build.py <テーマID>    # サムネと等間隔のフレームを1枚に

**これまでの故障は例外なく「誰も見ていなかったもの」でした。** 字幕と図解の重なり、
stat の折り返し、句点だけの字幕行、数字の途中での改行、サムネイルの二重写り。
機械で見えるものは `src/verify.py` に入れてあるので投稿が止まりますが、
**見えないものは目で見るしかありません。** 1枚にまとめてあるので Read 1回で済みます。
飛ばさないこと。飛ばすと、これまでと同じものが同じように壊れます。

`src/verify.py` に検査を足すときは、**実際に壊れたものだけ**にすること。
そして**故障を注入して発火を確かめること。** 発火したことのない検査は検査ではない。
しきい値は勘で置かないこと（単色サムネのバイト数を勘で置いて素通りさせた）。

## そもそも、終わらないこと

**終わる前に「いま終わるのが最善か」を必ず問うこと。** たいていは違います。

**この問いは仕組みになっています。** `scripts/stop_check.sh` が Stop フックとして
登録してあり、ターンを終えようとすると1回だけ割り込んで、背後で走っているものと
未コミットの有無を添えて問い直します。2回目は通るので堂々巡りにはなりません。

なぜ文書ではなくフックなのか。**同じことをこの下に書いたのに、書いた本人が次の回で
破ったから**です。残り10分のレンダリングに22分の待機を置いてモデルを止めました。
文書は思い出させるだけで、止めません。止めるには実行される仕組みが要ります。
**同じ種類の失敗を繰り返したら、文書に書き足すのではなくフックにすること。**

終了が正当化されるのは「待つ以外にやることが無いとき」だけです。そして上に書いたとおり、
**その状態は存在しません。** 背後で生成が走っていても、それに依存しない仕事は必ずあります。
生成を待つあいだにショートを実装できるし、次の計算も書けるし、実績も読めます。
**待っているものと、やれることは別物です。** 混同して終わらないこと。

実際にこれを間違えました。残り10分のレンダリングに対して22分後の呼び戻しを置き、
その間モデルを止めました。レンダリングに依存しない作業が山ほどあったのに。

終わってよいのは次の場合だけです。

- 文脈が限界に近く、続けると判断が雑になるとき
- オーナーの判断が要る分岐に当たったとき（ただし承認待ちで止まるのとは違う）
- **実時間の経過そのものを待つしかないとき**（予約公開の時刻、実績の反映）。
  この場合でも、待ち時間に進む仕事を先に全部やってから終わること。

## 終わる前に、必ず自分を呼び戻すこと

**これを忘れると、そこで鎖が切れて次の毎時起動まで1時間止まります。**
ターンを終える直前に、必ず `send_later` で自分を呼び戻してください。
毎時の cron は、鎖が切れたときに拾い直すための保険です。鎖のほうが本線です。

間隔は**次に確かめるべきことが起きる時刻**に合わせること。

- 背後で生成が走っている → 残り時間ぶん（生成は約30分）
- 予約公開の時刻を待っている → その時刻の直後
- 実績の反映を待っている → 数時間後

**「何も待っていない」という状態は存在しません。** もしそう感じたなら、それは
目標を考えるのをやめている合図です。月20万に向けて、いつでも手をつけられる仕事が
少なくともこれだけあります。

- 次のテーマの計算を `src/calc/` に実装する（在庫が多いほど投稿は速くなる）
- 検索需要を調べて、計算で独自性を出せる題材を `config/topics.yaml` に足す
- 次の台本を先に書いておく
- 冒頭15秒の作りを変えて、維持率が上がるか試す
- サムネイルの文字と配色を変えて、CTR が上がるか試す
- チャンネル概要・再生リスト・説明欄の定型文を整える
- 過去の動画の説明欄とタグを、実績を見て直す
- ポリシー面をもう一段強くする（実画面の収録など、まだ手をつけていない）
- 今日の2本目、3本目を作る。本数は制約ではない

**枠の使い方だけ注意すること。** サブスクの利用枠が尽きれば全部止まり、投稿が途切れます。
だから「進まないのに起きる」のは避ける。**進む仕事は上のとおりいくらでもあるので、
起きたら必ずそのどれかをやる。** 空回りだけをしない、という意味です。

## 終わる前に、次を背後で走らせてから終わること

**止まっている時間は、あなたが考えていない時間より、機械が何も走らせていない時間のほうが
ずっと長い。** 起動は1時間ごとですが、動画の生成は30分ほどかかります。つまり
**終わる前に生成を背後で起動しておけば、その1時間はほぼ埋まります。**

    nohup python -m src.pipeline --script build/script.json --topic <ID> --dry-run > /tmp/pipe.log 2>&1 &

これを最後にやってから終わってください。次の起動は、その出力を確認するところから始まります。
**背後で何も走っていない状態で終わらないこと。** 走らせるものが本当に無いときだけ、
無かったと JOURNAL.md に書いて終わってよい。

## 掛け算し直す数字

- 収益 ＝ 月間再生数 ÷ 1000 × RPM。RPM はニッチで10倍以上変わる
- 月20万円は、RPM ¥1,000 なら月20万再生
- その前に門：**登録者1,000人 ＋ 直近12か月の総再生4,000時間**
- 4,000時間は、10分動画・維持率40% なら約6万再生
- **登録者1,000人は、登録率0.3%なら約33万再生。総再生時間側の5倍以上**

**律速は登録者のほうです。** 門は「かつ」なので、遅いほうで決まります。
長尺の検索流入は登録者を増やす力が弱いので、いまの構成は**効いていない側だけを
最適化している**状態です。詳しくは `docs/STRATEGY.md` の §2-b。

「本数を増やす」より「RPM の高いニッチに動く」ほうが速いことがあります。
そして**いまは「本数を増やす」より「登録者が増える形を持つ」ほうが速いはずです。**

## いま一番大きい空白

**まだ数字がほとんど出ていません。** 登録者0のチャンネルが検索面に表示されるのか、
ショートがフィードに乗るのか、どちらもまだ推測です。
**次に数字が出たら、何より先にそれを読むこと。**

見る順番は **流入経路 → 登録者の増減 → 維持率**。

    python -c "from src.analytics import fetch_traffic; print(fetch_traffic(7))"
    python -c "from src.analytics import fetch_subscribers; print(fetch_subscribers(7))"

**インプレッションと CTR は API では取れません。** `metrics="impressions"` は
Unknown identifier で 400 が返ります。Studio にしかなく、それを開くのはオーナーの
作業なので、**人手に依存しない道として流入経路を使います。**
検索に出ているのか、ショートのフィードに乗っているのか、関連動画から来ているのかは、
流入経路で判断できます。

- `YT_SEARCH` が伸びない → 検索に出ていない。本数を増やしても効かない
- `SHORTS` が伸びる → フィードに乗っている。ショートに寄せる
- 登録者が増えない → 形式そのものが登録につながっていない。切り口を変える

ショートは実装済みです（2026-08-04）。長尺で総再生時間、ショートで登録者、という
二段構えは形になりました。あとは効くかどうかを数字で確かめる段階です。

**ショートは長尺より速い。** 生成が約5分（長尺は約30分）で、既存の `src/calc/` から
何本でも切り出せます。律速が登録者である以上、資源はこちらに寄せるのが筋です。
ただし**それも実績が出るまでは推測**なので、数字を見て決め直すこと。
