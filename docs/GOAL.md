1回で完結させる。ただし**「小さく終える」ことではありません** ——
小さく終える回が10回続いたとき、その10回で在庫が減っただけで目標には何も近づきませんでした。

0. **`python scripts/post_pending_comments.py`** — 数秒・冪等。予約公開した動画の
   コメントは公開まで書き込めない（private だと403）ので、公開時刻をまたいで
   付けに来る必要があります。冪等なので、6時間空いても次の回で必ず付きます
   （付くのが最大6時間遅れるだけ。取りこぼしはしない）。
1. **分析（毎回・これが本体）** — `python scripts/status.py`。
   動画ごとの再生数・予約の空き・流入経路・前提の期限・門までの距離が出ます。
   API を叩いて頭の中で組み立てないこと。**組み立てると間違えます**（実際に
   チャンネル総再生 5634 を、動画ごとの合計と取り違えかけた。
   **「あれは前身のぶん」と書いていたのは誤り**で、2026-08-10 に否定しました）。
   **読んだ結果を JOURNAL.md に書く。** 数字が動いていないなら「動いていない」と書く。
   期限が来ている前提があれば、そこで判定する（`config/hypotheses.yaml`）。
2. **最低1件を出す（毎回）** — 次の**6つ**のどれか。**最後までやること。**
   **正本は `docs/trigger_main.md` §4 と `run_marker.SHIP_KINDS`。ここは写しです。**

       upload   動画を1本。**予約まで入れる**（`upload_only.py`。**1日1本まで**）
       improve  **次の枠で出る1本を、実際に良くする**（規則3。定義は `docs/trigger_main.md` §4）
       means    `docs/MEANS.md` の未着手を1件、実際に動かす（実装・実行まで）
       verdict  期限の来た前提を、実データで判定する（`config/hypotheses.yaml`）
       premise  **縛っている腕の天井を疑う前提を1件 立てる**（0単位）。
                **台帳が薄いときだけ通る門があります**（`run_marker.ledger_days()`・2026-09-05）
       fix      実測で見つかった欠陥を1つ塞ぐ（道具・生成・投稿のどれか）

   > **`premise` は 2026-09-01 に6択目として足されましたが、この写しは
   > 2026-09-02 夕まで 5つ のままでした。** `eta.py` は毎周
   > 「**軌跡の腕が動くのは、前提を1件 閉じたときだけ**」と印字します ——
   > **台帳に注ぎ口が無ければ、到達日は永久に動きません。**
   > そして**回はこのファイルを毎回 読みます。ここに無い手は、選ばれません。**
   > （実測 `data/runs.jsonl` 304件: `fix` **72%** ／ `premise` **4%**）
   > **次に6択が変わったら、ここも同じ回に直すこと**（`docs/trigger_main.md` §4 が正本）。

   **`improve` は 2026-08-31 に足しました**（オーナーの規則3）。
   `upload` は1日1回しか撃てないので、これが無いと**大半の回が
   「何も出せない回」**になり、枠を埋めるための `fix` 探しが始まります。
   **「見た」「考えた」は `improve` ではありません** —— 物が変わったところまで。

   出したら記録する: `python scripts/run_marker.py --ship "<何を出したか1行>"`。
   `scripts/stop_check.sh` が、印の無いまま終わろうとする回を引き止めます（3回まで）。

**「今回は分析だけして、何も変えない」は、もう既定にしないこと**（2026-08-15 に変えた）。
`data/runs.jsonl` の直近10回が全部それで、そのあいだ**在庫だけが減っていました。**
本当に出せない回は、**理由を JOURNAL に書いてから**終わること。
「見るところが無かった」は理由になりません。**台帳（`docs/MEANS.md`）が
短いことのほうを疑う。**

在庫（`src/calc/`）が尽きているなら、これも `means` に数えます。

- `src/calc/` に次のテーマの計算を実装する（`calc:` の無いテーマは台本生成が止まります）
- `config/topics.yaml` に、計算で独自性を出せる切り口を足す
- 維持率・CTR を上げる仕組みを1つ試す

## ショートの作り方

    python -m src.pipeline --script build/short.json --topic s-<名前> --short --dry-run
    python scripts/upload_only.py s-<名前>

- テーマIDは **`s-` で始める**。topics.yaml に置かなくてよく、長尺のテーマ枠を消費しない
- 縦1080x1920。字幕は下から420上げてあるので、ショートのUIと重ならない
- **60秒以内**。ナレーション合計およそ300文字が目安（読み上げて約50秒）
- **1本＝1つの計算結果。** これで切り口も図も毎回変わり、量産判定を避けられる
- 長尺の8.5分の下限は適用されない（あれはミッドロール広告のための下限）
- 既存の `src/calc/` の数字をそのまま使えるので、長尺1本から何本も切り出せる
- **最後の1節で、次に何の数字が得られるかを言う。** 長尺の「登録依頼を書かない」規則を
  ここに流用しない。あれは長尺の維持率のための規則で、ショートは登録者を集めるために
  出しています。律速は登録者なので、ここを外すのは目的に反します。
  ただし「登録お願いします」ではなく、**続きに何があるかを具体的に言う**こと
  （効くかどうかは未検証。実績で確かめること）

1回の起動は短く独立に。前回の続きを記憶で追わず、JOURNAL.md と実績から読み直すこと。

## 投稿する前に必ず通すもの

    python scripts/inspect_build.py <テーマID>    # サムネと等間隔のフレームを1枚に

**これまでの故障は例外なく「誰も見ていなかったもの」でした。** 字幕と図解の重なり、
stat の折り返し、句点だけの字幕行、数字の途中での改行、サムネイルの二重写り。
機械で見えるものは `src/verify.py` に入れてあるので投稿が止まりますが、
**見えないものは目で見るしかありません。** 1枚にまとめてあるので Read 1回で済みます。
飛ばさないこと。飛ばすと、これまでと同じものが同じように壊れます。

`src/verify.py` に検査を足すときは、**実際に壊れたものだけ**にすること。
そして**故障を注入して発火を確かめること。** 発火したことのない検査は検査ではない。
しきい値は勘で置かないこと（単色サムネのバイト数を勘で置いて素通りさせた）。

## 自動実行は止めない

**止まれば投稿が途切れ、目標から遠ざかります。** 人が思い出して直す前提にしないこと。
設定の正本は `docs/TRIGGER.md`。壊れたらそこから復元する。

- **間隔の値をここに書かないこと。実物は `list_triggers` で見る。**
  毎時 → 6h → 8h → 12h → 毎時 → 6h と動いてきました。
  4か所に散らばって3か所が古くなったことがあります（8/12）
- **枠が苦しい週は間隔を延ばす。** リセット後に戻す。
  **落としたときは、戻す仕組みを必ず一緒に用意すること**（人の記憶に頼らない）。
  **削るのは1回の中身ではなく間隔のほう**です（中身を削ると、起きても何も出ません）
- **常時稼働はしない。1回で完結させる。** ただし**「小さく終える」ことではありません**
  （2026-08-15 に取り消し。§「起きたら何をするか」の最低ラインを見ること）
- 以前は毎時起動し、Stop フックで**終了そのものを止めていた**。**やめた。**
  いまのフックは終了を止めるものではなく、**最善かを問い、
  何も出していない回を引き止める**もの（3回まで。そのあとは通します）。
  **消さないこと。**

### 終わる前に、毎回「終わるのが最善か」を考えること

**これは仕組みになっています。** `scripts/stop_check.sh` が Stop フックとして
登録してあり、ターンを終えようとすると割り込んで、背後で走っているもの・
未コミットの有無・**この回が何か出したか**を添えて問い直します。

問うているのは「終わるかどうか」ではなく**「終わるのが最善かを考えたか」**です。

- **何も出していない回**（`run_marker.py --ship` の印が無い）は **3回まで引き止めます。**
  そのあとは通します。**止まったまま死ぬほうが、目標に対して確実に悪い**からです
- 出したあとは、**1回だけ**「終わるのが最善か」を問います

天秤にかけるのはこの2つ。

1. **投稿の予約は切れていないか。** 切れそうなら他を削ってでも生成に使う。
   ただし**「数日先まで埋まっているから作らない」を10回続けると、在庫が尽きます**
   （8/12〜8/15 に実際そうなりました）。**減り続けているかどうかで見ること。**
2. **判定を先送りしていないか。** 期限の来た前提を放置して終わると、
   推測が推測のまま残る（`config/hypotheses.yaml`）。

なぜ文書ではなくフックなのか。**同じことをここに書いたのに、書いた本人が次の回で
破ったから**です。文書は思い出させるだけで、止めません。
**同じ種類の失敗を繰り返したら、文書に書き足すのではなくフックにすること。**

### 落としても止まらない理由

**投稿が予約済みなら、起きなくても公開される。** だから間隔を落としても
チャンネルは動き続ける。逆に**予約が切れそうなときは、他を削ってでも生成に使う。**

### 取りこぼしても壊れないようにしてあること

常時見ている人がいない前提なので、拾わなくてよいようにしてある。
**次に来る側は、この性質を壊さないこと。**

- `scripts/post_pending_comments.py` は冪等。公開後に何度でも安全に付け直せる
- `scripts/status.py` は**予約が入っていない日**と**予算の残り時間**を出す
- `src/uploader.py` は**埋まっている公開枠を自動で避ける**。積んでも衝突しない
- 背後の生成は**コンテナ再起動で消える**。「走らせたはず」は当てにならないので、
  必ず status.py の予約一覧で確かめること

## 掛け算し直す数字

- 収益 ＝ 月間再生数 ÷ 1000 × RPM。RPM はニッチで10倍以上変わる
- 月20万円は、RPM ¥1,000 なら月20万再生
- その前に門：**登録者1,000人 ＋ 直近12か月の総再生4,000時間**
- 4,000時間は、10分動画・維持率40% なら約6万再生
- **登録者1,000人は、登録率0.3%なら約33万再生。総再生時間側の5倍以上**

**律速は登録者のほうです。** 門は「かつ」なので、遅いほうで決まります。
長尺の検索流入は登録者を増やす力が弱いので、いまの構成は**効いていない側だけを
最適化している**状態です。詳しくは `docs/STRATEGY.md` の §2-b。

「本数を増やす」より「RPM の高いニッチに動く」ほうが速いことがあります。
そして**いまは「本数を増やす」より「登録者が増える形を持つ」ほうが速いはずです。**
