# オーナー指示の取り込みゲート

## 今回のオーナー指示（2026-09-02）

> **「その旨を実行に反映されるように送って。そして以降指示を入れた時にそのように何も考えず実行されることが起きないようにするためにどうしたらいいか教えて」**

この指示の対象は、直前に判明した次の欠陥です。

- `FABLE_CAP_PCT = 50` は **Fable を使ってよい上限**であって、50%まで使う目標でも、50%未満なら全作業をFableにする既定値でもない。
- 模型の選択は、使用率の閾値だけで一律に決めず、**その仕事が目標到達をどれだけ早めるか／使用量**で決める。
- 新しいオーナー指示を、いちばん実装しやすい字面へ直結させない。まず意図・種類・優先順位・成功条件を解釈してから実装する。

## 直ちに実行へ反映すること

通常運転は止めない。そのうえで、次にモデル振り分けを触る回は、次を満たす形へ直す。

1. **50%は上限としてだけ使う。** `Fable使用率 < 50%` はFable採用の十分条件ではない。
2. **仕事ごとに選ぶ。** 少なくとも役割、失敗時の損失、判断の不確実性、将来の全動画へ効く範囲を入力にする。
3. **高レバレッジの判断へ強い模型を残す。** 企画、仮説検証、形式選定、次の1本の構成など、目標到達日を動かし得る仕事を優先する。
4. **定型・機械的・可逆な仕事は、十分な範囲で軽い模型を使う。** 記録、転記、既知の検査、単純な整形だけを理由なくFableへ流さない。
5. **選択理由を残す。** `work_kind / model / cap_state / expected_goal_effect / why` を記録し、あとから実績と突き合わせられるようにする。
6. **模型別の効果が未測なら、小さく比較して測る。** 「高そう」「強そう」だけで恒久ルールにしない。

`quota.sub_model()` のように使用率だけを見て全サブへ同じ模型を返す実装は、**上限管理には使えても、目標最適化の完成形として扱わない。**

## 以後、新しい指示を実装する前に必ず分類する

新しいオーナー指示は、原文を保存したうえで、次のどれかとして明示する。

- **目標**: 最終的に最大化・最小化するもの
- **固定条件**: オーナーが明示的に外すまで守るもの
- **上限／下限**: 越えてはいけない境界。そこまで使う・達する目標ではない
- **既定値**: 情報がないときの初期値。根拠があれば変えてよい
- **実験**: 成功条件、判定期限、外れたときの戻し方を持つもの
- **一回限り**: 指定した対象と時点だけに効くもの
- **判断委任**: 手段は固定せず、目標に照らして最適な方法を選ぶもの

特に数値は、**上限・下限・目標・既定値のどれか**を必ず書く。数値だけを見て実装しない。

## 実装前の7項目

毎回、コードを変える前に次を1件の記録として残す。

1. `verbatim` — オーナー原文
2. `kind` — 上の分類
3. `intent` — 何を良くしたい指示か
4. `literal_risk` — 字面どおり実装した場合の誤読
5. `alternatives` — 実装候補を最低2つ（戦略・資源配分に触る指示の場合）
6. `chosen_by_goal` — 目標到達への寄与／費用で選んだ理由
7. `measure_and_rollback` — 成功指標、判定時点、戻す条件

**「オーナーが言ったから」だけを実装理由にしない。** 守るべき原文と、その原文をどう機械へ落とすかは別です。

## 迷ったときの扱い

- 固定条件や外部公開など、誤読すると不可逆な結果になる場合だけ、オーナーへ短く確認する。
- それ以外は止まらず、**可逆で小さい解釈**を選び、解釈と戻し方を記録して進める。
- 既存の目標・固定条件と衝突する字面は、そのまま実装しない。衝突を解消した実装に読み替える。
- 指示の実装案そのものが目標を悪化させると数字で分かったら、意図を守る別案へ変える。

## 今回の分類

- 「Fableは全体週間使用量の50%まで」: **上限**
- 「Opus／Sonnet／Haikuで十分なところはそれを使ってよい」: **判断委任**
- 「ただし目標を目指してね」: **選択基準**

したがって、**50%未満ならFable、50%以上ならOpusという一律振り分けだけでは不十分**です。50%を越えないことを守りつつ、各仕事を目標への期待効果と使用量で選ぶことが、この指示の実装です。
