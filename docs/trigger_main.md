# 子（毎時の回）の手順

**これはトリガーの本文ではありません。** 親（`docs/trigger_parent.md`）が
毎時 `create_session` で立てる**子**に、これを読ませます。

**この回の仕事は全部あなた（子）のものです。** 親は立てて畳むだけで、
分析も生成も日誌も一切やりません。
**「親がやってくれているはず」というものは1つもありません。**

親が渡す本文は「このファイルを読んで、そのとおりに1周して、最後に自分を archive しろ」
という趣旨の短いものです。**事実を親の本文に写さない**ため、手順はここに置いてあります。

#### **`fetch` が `(non-fast-forward)` で弾かれたら、まず `merge-base`**（2026-08-17。**これが既定の道です**）

**7回続けて、この下の「改名」に着いています**（8/16 06:3x 以降、例外なし）。
下の節は起きた順に積んであって**実態と逆**なので、**結論を先に置きます。**

    git -C /home/user/youtube merge-base origin/<枝> <枝>

- **空が返る**（＝共通の祖先が無い。**実測7/7がこれ**） → 手元は**別系譜の古いクローン**です。
  **`git diff` の行数を見ないこと**（下の 07:2x の節。別物どうしの差なので、
  古い本文が全部「手元にしか無い追加」に見えます）。**そのまま改名で乗り換える**:

      git -C /home/user/youtube branch -m claude/youtube-auto-post-revenue-ggedij stale-clone-<日付>
      git -C /home/user/youtube switch claude/youtube-auto-post-revenue-ggedij

  **改名は何も捨てません**（退避名で残るので後から読めます）。
- **`origin` の先端が返る** → 手元が本当に進んでいる。**統合する中身があります**（捨てない）
- **それ以外** → 普通の分岐。`git log origin/<枝>..<枝>` を読んでから決める

**裏取りが要るなら**、`git rev-parse HEAD` と `git rev-parse origin/<枝>` を比べること。
**detached の HEAD のほうが `origin` の先端と一致していれば**、手元の枝に用はありません。

以下は、この結論に着くまでに踏んだ順の記録です。**上の3行で足りるなら読まなくてよい。**

#### **`git diff` で判断しないこと**（同日 07:2x。**この行のせいで危うく逆をやるところでした**）

ここには長らく「`git diff --stat origin/<枝> <枝>` を見て、**手元にしか無い追加が
0行**であること。**1行でもあれば、それは統合する中身です**」と書いてありました。

**07:2x の回の実測は `+273 / −16,740 行`。** 規則に素直に従えば
「273行は統合する中身」＝**改名してはいけない**、になります。**逆です。**

    git merge-base origin/<枝> <枝>        → **空**（共通の祖先が無い）
    git rev-list --left-right --count ...  → 51 50（**両側に**独自コミット）

**共通の祖先が無いとき、`diff` は「別物どうしの差」を出します。**
同じファイルの**古い版の行**が、全部「手元にしか無い追加」として数えられる。
**`diff` の 273行 は、独自の成果ではなく、ただの古い本文でした。**
（実際、手元の枝の commit 題は `origin` の `docs/JOURNAL.md` の中に本文ごとありました。
**同じ仕事が、別の SHA で既に `origin` に入っている**）

**だから見るのは系譜のほうです。**

    git -C /home/user/youtube merge-base origin/<枝> <枝>

- **空が返る** → 共通の祖先が無い。**`diff` の行数は意味を持ちません。**
  上の改名で `origin` に乗り換えること

**念のための裏取り**: 手元の枝の commit 題を `origin` の `JOURNAL.md` から
`grep` して出てくるなら、**同じ仕事が別の SHA で既に入っています**（捨ててよい）。

#### **浅いクローンでは、上の3分岐がそのまま嘘になります**（2026-08-18 19:0x に踏んだ）

この回の手元は `.git/shallow` **あり**（深さ50）でした。そこで上の表を引くと:

    git merge-base origin/<枝> <枝>   → **手元の枝の先端そのもの**（空でも origin の先端でもない）
    git status -sb                     → `ahead 50, behind 50`
    git log origin/<枝>..<枝>          → 50件。**題も全部ちがう**（origin 側に同じ文字列は無い）

**表の3つ目「普通の分岐。読んでから決める」に落ちますが、これは分岐ではありません。**
浅いクローンは**履歴を途中で切ってある**ので、`merge-base` も ahead/behind も
**切り口から先を見ていません。** 50件の「独自コミット」は、
**origin 側では切り口の向こうにあるだけ**でした。

**見るのは日付です**（浅くても commit そのものには入っています）:

    git log -1 --format='%ci %s' <枝>            → 2026-08-15 10:17   ← 3日古い
    git log -1 --format='%ci %s' origin/<枝>     → 2026-08-18 09:48

（コンテナが `sources` で clone した先）。手順どおり `switch <枝>` を打った結果、
**3日前の作業木に降りました。** `docs/trigger_main.md` が古い版に戻り、
それを「誰かが書き換えた」と読みかけています。**枝名に合わせにいって、中身で3日戻る**
という形は、ここに1行も書いてありませんでした。

- **深さを足してから測り直すこと**: `git fetch --deepen 100 origin <枝>`。
  それでも `merge-base` が手元の先端を返すなら、**日付の新しい側が正**
- **改名も `checkout -B` も要りません。** `git switch --detach origin/<枝>` で乗り換え、
  **push は `HEAD:<枝>`**（§6 が既にこの形です）。分離 HEAD のままで1周まわせます
- **手元の枝の参照は触らないこと。** 消さなければ、後から読めます
- `data/runs.jsonl` を §1 より先に書くと `switch` が「上書きになる」と止まります。

だから **`--count` は「未使用の節を持つ calc の数」に固定して、回数のほうを増やす**こと。

##### **回すあいだ、`--list` の未使用が1つずつ減っているか見ること**（2026-08-18 に踏んだ）

    for i in 1 2 3; do python scripts/topic_forge.py --count 1 > .../forge$i.log 2>&1; done
    python scripts/topic_forge.py --list | grep <族名>     ← **回すたびに見ること**

**減っていなければ、そこで止めること。** 3回まわす前に気づけば、

#### **`--count` を下げても、衝突は防げません**（2026-08-17 11:5x に `--count 1` で踏んだ）

### **生成を背後に投げたまま archive しないこと**（親子方式で新しく出た穴）

以前は同じセッションが1時間後も生きていたので、
「生成は待たなくてよい。次の回で予約一覧を確かめる」で足りていました。
**いまは違います。あなたは1周したら自分を畳みます。**

**畳んだ時点で、走っている生成もコンテナごと消えます。**
`build/` は gitignore なので、**push もされず、次の子にも残りません。**
**丸ごと捨てることになります。**

だから:

- **生成を始めたら、最後まで待つこと**（台本〜レンダリングで5〜10分）

  #### **「待つ」は「手を止める」ではありません**（2026-08-17 10:0x に測って足した）

  **畳んではいけない**のであって、**そのあいだ何もしないでいろとは言っていません。**
  生成の中身はほぼ全部 `claude -p` と描画の待ち時間で、こちらの手は空いています。

      nohup python scripts/batch_build.py --count 5 --date <日> --jobs 3 > <log> 2>&1 &
      ...そのあいだに §4 の fix / means を進める...
      until ! pgrep -f "python.*batch_build" > /dev/null; do sleep 15; done   ← **前面の sleep は止められます**

  ##### **`pgrep -f batch_build.py` と書かないこと**（2026-08-17 18:5x に踏んだ）

  **`-f` はコマンド行ぜんぶを見ます。** この待ち合わせを走らせている
  シェル自身の行に `batch_build.py` という字が入っているので、
  **自分に当たって永久に抜けません**（背景に投げていたので、`kill` するまで残りました）。

  `python.*batch_build` にすると、シェルの行（`until ! pgrep …` で始まる）には
  当たらず、**`/usr/local/bin/python … batch_build.py` にだけ当たります。**

  **抜けたかどうかは `pgrep` ではなく、ログの `=== まとめ ===` で見ること。**
  待ち合わせの道具が自分を数えている、は形として気づきにくい ——
  **ログには既に「予約できたのは 7 / 8 本」が出ていました。**

  この回の実測: batch が **13分**（作る 6.6分 ＋ 予約 6分）走っているあいだに
  `--closes` の fix を1件仕上げ、**そのうえで自分の穴を踏んで直すところまで**入りました。
  **直列に並べていたら、この回の ship は2件でした。**

  - **`sleep` は背景で撃つこと**（`run_in_background`）。前面の `sleep` はこの環境が止めます
  - **投げっぱなしにしないこと。** 待ち合わせを必ず入れる ——
    `build/` は gitignore なので、**archive した瞬間に走っている生成ごと消えます**
- **待てないなら始めないこと。** 次の回に回す
- **投稿（`upload_only.py`）まで済ませてから archive する。**
  作っただけで畳むと、その回の仕事はゼロになります

## 6. 終わり方（**この順で。最後の archive を飛ばさないこと**）

**これが無いと Stop フックが引き止めます**（§4）。**印だけ先に打たないこと。**

同じ語を書けば、それはちゃんと再発として残ります。**
打ってから畳むと、次の回には「出した回」に見えて、何も残っていません。

**(a) 記録する。** `docs/JOURNAL.md` に**理由と間違い**を書く。
**変えなかったならそう書く。**
