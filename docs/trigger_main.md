# 子（毎時の回）の手順

**これはトリガーの本文ではありません。** 親（`docs/trigger_parent.md`）が
毎時 `create_session` で立てる**子**に、これを読ませます。

**この回の仕事は全部あなた（子）のものです。** 親は立てて畳むだけで、
分析も生成も日誌も一切やりません（オーナー指示
「ここでしてた作業を全部子セッションにやらせる」）。
**「親がやってくれているはず」というものは1つもありません。**

親が渡す本文は「このファイルを読んで、そのとおりに1周して、最後に自分を archive しろ」
という趣旨の短いものです。**事実を親の本文に写さない**ため、手順はここに置いてあります。

```

**次の子が来るまでの時間は `list_triggers` で見ること。**
**ここに間隔を書かないこと。** 書くと古くなり、実物と食い違います（8/12 に3か所で食い違った）。

**この回は、何か1つ出してから終わること**（§4 の最低ライン）。
オーナー指示 2026-08-15（原文）: **「子が、少しの作業で終わるの直して」**

## 0. 枝を確かめる

**「普通は既に合っている」と書いてありましたが、違いました**（2026-08-10、親子方式の1回目）。
`source_revision` で立てても **HEAD は detached で来ます。** `rev-parse --abbrev-ref HEAD`
が `HEAD` と返ったら、それが detached です。**枝名と読み違えないこと。**
そのままコミットすると、どこの枝にも乗りません。**毎回いちど確かめて、合わせること。**

    git -C /home/user/youtube rev-parse --abbrev-ref HEAD

`claude/youtube-auto-post-revenue-ggedij` でなければ:

    git -C /home/user/youtube fetch origin claude/youtube-auto-post-revenue-ggedij
    git -C /home/user/youtube checkout -B claude/youtube-auto-post-revenue-ggedij origin/claude/youtube-auto-post-revenue-ggedij

**main で作業すると、成果がどこにも残りません。**

### なぜ手で見るのをやめたか（2026-08-15、自走の1周目で踏んだ）

ここには「`tags` に `youtube-hourly` を含む行のうち、**自分以外**に
PENDING / RUNNING / IDLE があるか。いたら `created_at` を比べて、
**新しいほうが畳む**」とだけ書いてありました。**自走した子は必ずこれに当たります。**

**立てた相手は、定義から自分より古く、立てた瞬間はまだ生きています。**
§6 (f) は archive の**前**に置いてあるので（止まっても失うのが archive だけで
済むように）、この重なりは事故ではなく**毎回起きます。**

    04:59:50  前の子が起きる
    05:09:01  前の子が §6 (f) で次の子を立てる   ← 次の子が生まれる
    05:09:26  前の子はまだ RUNNING（残りは archive だけ）

畳む側は (a)〜(e) を飛ばすので、**次の子も立てません。**
**1周目で鎖が終わり**、`bcf433e` が消しにきた48%の空転がそのまま戻ります。

直したのは1点、**自分を立てた相手（`parent_session_id`）を数から除く**ことです。
除いて安全なのは §6 の順番そのものが理由で、**(f) は (a)〜(e) の後ろ**だから、
私を立てた時点で向こうは記録も push も題名も済んでいます。
**残っているのは archive だけで、生成も予約もぶつかりません。**

**`parent_session_id` で「絞る」のは今も禁止です**（孫の親IDは親ではなく
立てた子になるので、親IDで絞ると兄弟の半分が見えない）。
ここでやっているのは**絞り込みではなく1件の除外**で、向きが逆なので両立します。

理由。8/15 03:48 と 03:50（UTC）に**オーナーの連絡が4分あいだで2件届き、
親が子を2つ立て、同じ枝で2人が同時に1周を回しかけました**（枠を2回食い、
予約時刻がぶつかる）。親側は `docs/trigger_parent.md` (3) で塞ぎましたが、
**親の2回のターンが同時に走ると、親からは互いが見えません。**
**こちらで1回見れば、その取りこぼしも止まります。**

理由。CCR の MCP の返り（`list_sessions` / `get_session` / `create_session`）の
`external_metadata` に、枠の情報が最初から入っています。

    "rate_limit_info": {"rateLimitType":"seven_day",   # five_hour と2種類ある
                        "resetsAt":1786744800,          # ＝ 2026-08-15 07:00 JST
                        "status":"rejected"}            # allowed / allowed_warning / rejected

    "usage": {"cache_read_tokens":767141, "cache_write_tokens":142437,
              "input_tokens":19, "output_tokens":3072}

**`list_sessions` は1回で25件ぶん返します。** 1件が1点なので、
**1回叩くだけで25点の時系列が入ります。** 遅れもありません。

### この計器が言えること・言えないこと

**言える。** いまどちらの枠が効いているか。警告帯に入っているか。閉じているか。
いつリセットされるか。**判断に要るのはほぼこれで足ります。**

**言えない。** **残り何%か。返り値に%は入っていません。** 分母（何トークンで
閉じるか）も返りません。だから `quota.py` は
**`status` が切り替わった時刻と、そこまでに見えた消費量**を枠ごとに積みます。
**1点では目盛りは決まりません。積み続けることに意味があります。**

**だから、読めた回も必ず `--ingest` すること。** 読むだけで積まないと、
次の回が古い点を見ることになります。

「生成は待たなくてよい。次の回で予約一覧を確かめる」で足りていました。

**畳んだ時点で、走っている生成もコンテナごと消えます。**
`build/` は gitignore なので、**push もされず、次の子にも残りません。**
**丸ごと捨てることになります。**

- **生成を始めたら、最後まで待つこと**（台本〜レンダリングで5〜10分）
- **待てないなら始めないこと。** 次の回に回す
- **投稿（`upload_only.py`）まで済ませてから archive する。**

## 6. 終わり方（**この順で。最後の archive を飛ばさないこと**）

**(a) 記録する。** `docs/JOURNAL.md` に**理由と間違い**を書く。
**変えなかったならそう書く。**

**姉妹ループも同じ枝に押します。** 弾かれたら force ではなく
`git pull --no-rebase` して中身を読んでから統合すること
（`docs/FROM_THE_ETA_LOOP.md` が向こうからの連絡経路です）。

**(c) 未コミットを残さない。**

    git -C /home/user/youtube status --porcelain

**(d) セッションの題名に結果を書く（`set_session_title`）。**
```
