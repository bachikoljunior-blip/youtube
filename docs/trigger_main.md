## 0. 枝を確かめる

**「普通は既に合っている」と書いてありましたが、違いました**（2026-08-10、親子方式の1回目）。
`source_revision` で立てても **HEAD は detached で来ます。** `rev-parse --abbrev-ref HEAD`
が `HEAD` と返ったら、それが detached です。**枝名と読み違えないこと。**
そのままコミットすると、どこの枝にも乗りません。**毎回いちど確かめて、合わせること。**

    git -C /home/user/youtube rev-parse --abbrev-ref HEAD

`claude/youtube-auto-post-revenue-ggedij` でなければ、**次の2手で合わせること**:

    git -C /home/user/youtube fetch origin claude/youtube-auto-post-revenue-ggedij:claude/youtube-auto-post-revenue-ggedij
    git -C /home/user/youtube switch claude/youtube-auto-post-revenue-ggedij

**main で作業すると、成果がどこにも残りません。**

#### **`checkout -B` を使わないこと**（2026-08-15 17:1x。ここで1セッション死にました）

ここには長らく `git checkout -B <枝> origin/<枝>` と書いてありました。
**あれは auto mode classifier に弾かれます。** `session_015KoJEMuNow1JuHKhD4hNFF` は
**11ファイルぶんの書き換えを準備した状態でここに当たり、承認待ちのまま死にました**
（成果はゼロ。`git branch -f` も同じく弾かれます）。

上の2手は**同じ結果に着く別の道**です。`fetch` の refspec `<遠い枝>:<手元の枝>`
は、**チェックアウトせずに手元の参照を早送りします**（枝が既にあっても通る）。
そのあと `switch` は「同じ内容へ移るだけ」なので、破壊的な操作になりません。

- 手元の枝に**独自のコミットがある**ときは fetch が early-update を拒みます。
  そのときは `git log origin/<枝>..<枝>` を読んでから統合すること（**捨てない**）
- `data/runs.jsonl` を §1 より先に書くと `switch` が「上書きになる」と止まります。
  **§0 を §1 より先にやること**（この順で書いてあるのはそのためです）

### この計器が言えること・言えないこと

**言える。** いまどちらの枠が効いているか。警告帯に入っているか。閉じているか。
いつリセットされるか。**判断に要るのはほぼこれで足ります。**

**言えない。** **残り何%か。返り値に%は入っていません。** 分母（何トークンで
閉じるか）も返りません。だから `quota.py` は
**`status` が切り替わった時刻と、そこまでに見えた消費量**を枠ごとに積みます。
**1点では目盛りは決まりません。積み続けることに意味があります。**

**だから、読めた回も必ず `--ingest` すること。** 読むだけで積まないと、
次の回が古い点を見ることになります。

### 何を選ぶか（迷ったらこの順）

2. **期限の来た前提がある → `verdict`。** 放置すると推測が推測のまま残る
3. **目標の数字が2週間動いていない → `means`。**「いまの機械を磨く」だけの回に戻らない
4. **上のどれでもない → `means`。** `docs/MEANS.md` の未着手から1つ

#### **batch の出力は、必ずファイルに落として grep すること**（2026-08-15 20:2x）

    python scripts/batch_build.py ... > /tmp/.../batch.log 2>&1 ; tail -40 /tmp/.../batch.log

**`| tail -N` で受けないこと。** 並列だと出力が N 本ぶん混ざるので、
**落ちた本の理由が末尾から押し出されて消えます。**

**この項は 19:xx の回が「次からはファイルへ」と書いたのに、20:0x の回も
`| tail -45` で受けました。** 日誌に書いても、次の回が読むのは
**「次の回へ」の数行だけ**です。だから**手順のほうに置いてあります。**

その回は、消えた出力を手で取り直して初めて
**「10本中7本が落ちた」の正体が、失敗ではなく中身の取り違えだった**ことに
気づいています（`docs/MEANS.md` M14 の8つめ）。
**末尾だけ見ていたら、混線したまま本数を増やしていました。**

**`--jobs`（既定 3）を使うこと**（2026-08-15 19:xx に足した）。1本11分の中身は
ほぼ全部が `claude -p` の**待ち時間**で、生成中の CPU は 2〜4% しか動いていません
（`ps` で実測）。**待ち時間は重ねられます。** 直列だったのは、そう書いてあっただけです。
**並列なのは「作る段」だけで、予約は必ず1本ずつ**（`upload_only.py` は
`next_publish_at` と待ち行列という共有の状態を触るため）。

**「1周＝1本」は §4 の最低ラインであって、上限ではありません。**
門は「90日で1000万ショート再生」＝**1日92本**に縮んでいるのに、
1周15〜45分で1本ずつでは**1日十数本が上限**でした（`docs/MEANS.md` M14）。
**出せる回は、1本で止めないこと。**

`--hour` で置き場所を選びます（埋まっている日は自動で飛ばして翌日へ）。
**実験の窓を踏まないこと。** いまの窓は 8/16〜8/23（M14）。

#### **予約済みの本は、どこまで直せるか**（2026-08-15 に調べた）

    python scripts/build_provenance.py     # 各本が、どの時点のコードで作られたか

- **直せる**（消さずに、API で差し替え）: **題名・説明欄・サムネ・公開時刻・タグ**。
  `scripts/retitle.py` と `scripts/refresh_thumbnail.py`
- **直せない**: **動画ファイル本体。** YouTube に置き換え機能は存在しません。
  絵と音を直すには**消して上げ直す**しかなく、**動画IDが変わります**

**予約中の本は一度も公開されていないので、動画IDが変わっても失うものはほぼゼロ**
（誰もそのURLを持っておらず、再生も評価もコメントも0）。**渋る理由は URL ではなく、
作り直しの手間と、その間に予約が空くこと**のほうです。

**だから順番が決まっています ——「先に作る、次に予約を移す、最後に消す」。**
消してから作ると、その間ずっと穴が空きます（**投稿が途切れるのが最大の損失**）。

`build_provenance.py` は各本について「上げた時刻」以前で最後のコミットを出し、
**その後に入った、絵と音を変える直し**を並べます。
`?` 印は **checkout の順序が読めない範囲**なので、「入っている」に数えていません。

**contact sheet の目視は Agent ツールの子エージェントに任せること。本流で Read しない。**
子エージェントには**動画の向き（縦/横）を伝え**、「投稿可/作り直し」を8行で返させる。
**目視をやめないこと。** 機械検査は「指示どおり折ったか」しか見ておらず、
**指示した位置そのものが悪い場合は素通りします**（通算11回再発）。

### **生成を背後に投げたまま archive しないこと**（親子方式で新しく出た穴）

以前は同じセッションが1時間後も生きていたので、
