# オーナーへの指示

**親が毎回の発火で出すのは、下の「出す」に入っていて、いま窓の時刻に当たるものだけです。**
作業ログは出しません（読む側の時間を食うだけで、こちらの数字は1つも動かないため）。
**達成の連絡も、質問も、親セッションで受けます。**

---

## 出す

> **親が読むのは、この節だけです。** ここに窓が無ければ、親は何も言わずに終わります。
> **`## 未処理` 以下は親に出させません**（下の「出す列の作り」）。

**親の手順**（`docs/trigger_parent.md` (1) に同じことが書いてあります）:

1. いまの時刻を **JST** で出す（`TZ=Asia/Tokyo date` の1行だけ。**それ以外は打たない**）
2. 下の `### 出す <日付> <始まり>〜<終わり> JST` のうち、**始まり ≤ いま < 終わり**のものを探す
3. 見つかったら、その **`>` の行の中身だけ**をそのまま出す。**見出しも窓も出さない**
4. 1つも無ければ、**何も書かずにターンを終える**

## 出す列の作り（**子が読む。親は読まなくてよい**）

### なぜ窓なのか（**この設計の要点**）

**親は「前回これを出したか」を覚えていません。** 同じセッションが続くので、
文脈は要約されて消えます。**だから記憶に頼る設計は必ず壊れます。**
2026-08-16 にオーナーから「同じ操作依頼を繰り返すな」と指示が来た時点で、
親は1件の依頼を**十数回くり返していました。**

**記憶を持たせるのではなく、記憶を要らなくします。**
依頼ごとに出す時間帯（窓）をこのファイルに書いておき、
**親はいまの時刻が窓に入っているかだけを見ます。**

    窓は1時間。親の cron は毎時（`9 * * * *`）
    → 1つの窓に発火はちょうど1回しか入らない ＝ **1回だけ出る**

**親が要るのは現在時刻とこのファイルだけです。** 前回の記憶も、状態ファイルも、
書き込み権限も要りません（**親はリポジトリを書けない**ので、これが効きます）。
**窓が過ぎれば自動的に黙ります。** 子が片付けに来なくても正しく止まるので、
**正しさが子の実行タイミングに依存しません。**

**この2つは、うっかり壊せます。**

- **窓を「未処理があるかどうか」で決め直さないこと。** それは毎時に戻ります
- **親に状態を書かせようとしないこと。** 親はリポジトリを触れません。
  **触れるようにするのも駄目です**（親が重くなるのが、この設計を作った理由です）

### 子が守ること

- **窓は1時間ちょうど、正時から正時まで。**（`11:00〜12:00`）
  cron は毎時9分に発火するので、正時区切りなら**発火が必ず1回だけ**入ります。
  **1時間より長くすると2回出ます**（＝オーナーの言う「繰り返し」に戻ります）。
  **`9 * * * *` は `list_triggers` で確かめること** ——
  間隔が毎時でなくなったら、窓の幅もそれに合わせないと**出ない回**が生まれます
- **窓を重ねないこと。** 重なると同じ回に2件出ます
- **本文は `>` の引用で書く。** 親が出すのはその中身だけなので、
  **引用の中に「操作依頼」以外を書かないこと**（理由・背景・数字の説明は
  `## 未処理` のほうに書く。オーナーの指示 2026-08-16「操作依頼の内容だけを表示する」）
- **窓は「オーナーが動ける時刻」に置く。** 依頼を書いた時刻ではありません。
  8/16 昼に見てほしい数字なら、窓は 11:00〜12:00 に置きます
- **もう一度頼みたくなったら、窓を新しく1つ足す。** 消して作り直さない。
  **足した理由を `docs/JOURNAL.md` に書くこと** ——
  「まだ返事が無いから」は理由になりません。**返事が無くても回る設計**が前提です
  （目標本文「私が必ず読むとは限りません」）
- **取り下げ・不要化も、窓を1つ足して1回だけ伝える。**
  黙って `## 済み` へ移すと、オーナーには**依頼が消えたことが見えません。**
  「済み」に移すのと、取り下げを1回出すのは**別の作業**です
  （オーナーの指示 2026-08-16「不要になった操作依頼も、繰り返さずに1回だけ書く」）
- **窓が過ぎたら片付ける**（下の1行。**忘れても害はありません** ——
  過ぎた窓は出ないので、溜まるだけです）

      python scripts/for_owner.py --expire    過ぎた窓を「出した（記録）」へ移す
      python scripts/for_owner.py --list      窓の一覧（過去・いま・これから）
      python scripts/for_owner.py             いま親が出すはずの本文（確認用）
      python scripts/for_owner.py --at '2026-08-16 11:09'   その時刻で試す
      python scripts/for_owner.py --check     書式の検査（重なり・長すぎる窓を見る）

**窓を足したら `--check` を通すこと。** 重なりと長すぎる窓は、
どちらも「1回だけ」を壊しますが、**目では気づけません。**

### なぜ「出す」と「未処理」を分けたか

**同じ列にすると、書いた瞬間から毎時出ます。** これまでがそれでした。
分けたことで、次の2つが別々に決められます。

    ## 未処理   いま開いている依頼の**全文**（理由・数字・分岐まで）。**子が読む**
    ## 出す     そのうち**いつ、何を、1回だけ**オーナーに見せるか。**親が読む**

**依頼が開いていること**と、**それをいま見せること**は別です。
開いていても、動ける時刻が来るまでは見せないほうが読まれます。

## この列の決まり（子が守ること）

- **ここに書いてよいのは、オーナーの手でしかできないこと**だけです。
  **書く前に、自分で取る道を1回は試すこと。** 2026-08-15、「API では取れない」と
  書いていた数字が、**別の API（Reporting API）では取れることが分かりました。**
  **「取れない」と書く前に、試したのがどの API かを言えること。**
- **頼む前に、その操作がオーナーの画面に実在するかを確かめること。**
  2026-08-15、「Claude Code の設定に権限ルールを1行足して」と頼みましたが、
  **その欄自体が claude.ai/code に存在しませんでした**（権限モードは
  自動／編集を承認／プラン の3つから選ぶだけ）。オーナーは善意で、
  一番それらしい「セットアップスクリプト」欄に文字列を貼り、
  **こちらの起動を壊しかけたうえで、何も進みませんでした。**
  **実在しない操作を頼むのは、相手の時間を使って0を返すことです。**
  画面の名前が分からないなら、**まず「その画面に何が見えますか」と聞くこと。**
- **1件ずつ、効果を数字で。**「やってくれれば伸びます」ではなく
  「これが分かると、いま測れていない○○が測れる」と書く
- **未処理は3件まで。** 窓は1件につき原則1つなので、多いと出す機会の取り合いになります
- **やってもらえない前提で設計すること**（目標本文「必ず読むとは限りません」）。
  ここに書いた項目に依存する計画を立てない。**上振れのおまけとして扱う**
- 済んだら子が「済み」へ移す。**オーナーが親セッションで「済んだ」と言ったら、
  親が次の子にそれを渡し、子がここを直します**（親はリポジトリを触れないため）。
  **このとき、まだ先の窓が残っていたら消すこと** —— 済んだ依頼を後から出すのは、
  オーナーから見れば「聞いていない」のと同じです（`--list` で見えます）
